# v0.2.26

## The welcome page drops a private service's card

The welcome page previously listed every known service as a static card
regardless of its NCC-05 visibility, linking visitors to a locator they could
not decrypt. The sidecar now exposes an unauthenticated
`GET /ncc-api/public/visibility`, reporting only each service's ID and
`public`/`private` mode — no recipients, endpoint or health — and the welcome
page uses it to skip the card for a private service.

This is unlisting the card, not closing a leak: a private service's NCC-02
anchor still publishes that it exists, exactly as before. See
[`docs/private-services.md`](../private-services.md#interaction-with-the-welcome-page).

If the sidecar cannot be reached, the welcome page falls back to showing
every card, the same as every earlier release.

## Private services no longer show a certificate fingerprint

A private service's public NCC-02 record left out the endpoint but still carried
the TLS certificate fingerprint (`k`). Anyone could read it, match it against
servers found by scanning, and use it to link records that shared it. The record
now has no `k`. The fingerprint is still in the encrypted locator, which clients
use to check the server.

Public services do not change. A client built to the earlier NCC-02 text may
still expect `k` in a private service's public record.

## Search checks the right key

- A fingerprint in a service's NCC-02 record is now checked even when the
  endpoint comes from its locator. Before, search checked only the locator's
  fingerprint: it skipped the check if there was none, and used the locator's if
  the two differed.
- Search now accepts service records without a `private` tag (`ncc-02-js`
  0.5.2). One with no endpoint is treated as private and is not listed.

A service whose record and server show different fingerprints is now reported as
`k-mismatch`. This can happen if a service's addresses use different certificate
keys.

## NCC and nsite links in Ditto profiles

A Ditto profile's website can now be an NCC service or a NIP-5A site instead of
only an `https://` URL:

- `ncc://<npub>/<service>` opens the service in NCC Browser, resolved through
  its signed locator. The bare `ncc://<npub>` form means the `addr` service.
- `nsite://<npub>[/<site>][/path]` opens a static site. Ditto's host forms
  (`nsite://<npub>` and `nsite://<base36-pubkey><site>`) also work.

Inside NCC Browser the original address is used, so the browser opens the
service or site natively with its path intact. In an ordinary web page, Ditto
opens a linked nsite in its own viewer; an `ncc://` link needs NCC Browser to
resolve it. Malformed or unsupported values are not rendered as links.

This ships in the rebuilt `ncc-server-ditto-web` image; no other upgrade step is
needed.

## Upgrading

```sh
cd /opt/ncc-server
sudo make bundle-upgrade REF=v0.2.26
```

or use **Upgrade to v0.2.26** on the admin panel's Overview page. If you pin
images yourself, move the `ghcr.io/imattau/ncc-server-*` pins to `:0.2.26`.

The sidecar and caddy-panel images must both be upgraded for the new route
and the welcome page that calls it.

### Replace old private records

Upgrading may not replace a private service's existing record. After the new
sidecar is running, click **Republish** for each private service on the
Installed page. The service needs at least one recipient and a publication
relay. Relays and other people may keep copies of the old record, so this does
not make an already published fingerprint secret again.

## Verifying

1. Set a service private (`sudo make service-private SERVICE=…`) and reload
   the welcome page; its card should disappear.
2. `make service-public SERVICE=…` and reload again; the card should return.
3. Set your profile website to `ncc://<npub>/<service>` or an `nsite://`
   address and check that it renders as a link. In NCC Browser it should open
   natively; in an ordinary browser an nsite should open in Ditto's viewer.

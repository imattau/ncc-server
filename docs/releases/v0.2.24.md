# v0.2.24

## `search-crawler` no longer turns unhealthy during a first-import burst

After the v0.2.23 upgrade, some nodes reported `search-crawler` as unhealthy
with `Health check exceeded timeout (5s)`, even though the process was alive
and indexing.

Two things changed:

- Removing an unindexed private service no longer deletes from the full-text
  table first. FTS5 has no index on the `(pubkey, item_id)` columns used for
  that delete, so the lookup scanned the whole table. Private services are
  usually not in the index at all, and a crawl could repeat that scan for each
  one. The crawler now checks the ordinary row first and skips the FTS work
  when there is nothing to remove.
- The `search-crawler` health check allows 15 seconds per probe and a
  90-second start period. The health endpoint shares the event loop with
  SQLite/FTS writes, so a live process can legitimately look slow during a
  large first import after a restart.

If a node still reports unhealthy after that window, see
[`docs/troubleshooting.md`](../troubleshooting.md#search-crawler-is-unhealthy-after-an-upgrade).

## Upgrading

```sh
cd /opt/ncc-server
sudo make bundle-upgrade REF=v0.2.24
```

or use **Upgrade to v0.2.24** on the admin panel's Overview page. If you pin
images yourself, move the `ghcr.io/imattau/ncc-server-*` pins to `:0.2.24`.

After the upgrade, recreate the search containers so the new health check and
crawler code are in use:

```sh
sudo make bundle-up
```

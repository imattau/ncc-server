# Distributing services with npack

[npack](https://github.com/imattau/npack) is a Nostr-native package manager:
it publishes signed release metadata as `kind:9900` events, stores immutable
`.npk` artifacts on Blossom-compatible servers, and verifies SHA-256 hashes
locally. NCC Server uses it as the **distribution and discovery layer for
custom service packages**. The container image still lives in its registry.

```text
publisher repository                       operator node
────────────────────                       ─────────────
image ──► registry (unchanged)
  │
  └── .npk descriptor ──► Blossom
        kind:9900 ─────► relays
                                  │
                                  ▼
                          npackd (read-only, container)
                                  │ Unix socket
                                  ▼
                     sidecar ──► App catalogue ──► panel
                             └─► verified descriptor ──► installer
```

There is no central catalogue. A node reads relays and Blossom, verifies what
it finds, and keeps a local cache. The publisher's key is the package
identity.

## The package is a descriptor

An NCC service package is a `.npk` with `"kind": "ncc-service"`. npack treats
it as metadata: `npack install` refuses it, and `npack resolve` / `search`
hand it to an external tool. That is deliberate, because installing a
container service is not the same as writing files into a host prefix.

```text
hello-1.0.0.npk
├── .npack/manifest.json
└── share/ncc-server/services/hello/
    ├── service.json
    ├── compose.yaml        # generated for inspection; the installer regenerates it
    ├── icon.png
    └── README.md
```

`service.json`:

```json
{
  "schema": 1,
  "service_id": "hello",
  "name": "Hello Service",
  "summary": "One line for the catalogue",
  "description": "Longer text, at most 4000 characters",
  "categories": ["Social"],
  "homepage": "https://example.com/hello",
  "license": "MIT",
  "support_url": "https://example.com/hello/support",
  "icon": "icon.png",
  "compose_service": "app",
  "image": "ghcr.io/acme/hello@sha256:…",
  "public_port": 8450,
  "backend_port": 18080,
  "container_port": 80,
  "probe_path": "/",
  "env": { "LOG_LEVEL": "info" },
  "volumes": { "hello-data": "/data" },
  "min_bundle_version": "0.2.8"
}
```

Signed packages must pin the image by digest. The release signature covers
the descriptor, so the descriptor has to cover the image bytes; a mutable tag
would let the registry change what the signed package installs.

The Compose fragment is **generated by the node**, not shipped by the
publisher. It always sets:

- the pinned image and one loopback port (`127.0.0.1:<backend_port>`);
- `read_only`, `cap_drop: ALL`, `no-new-privileges`;
- a bounded `pids_limit`, a `/tmp` tmpfs, and only the named volumes declared
  in the descriptor.

A package cannot request host networking, extra capabilities, devices, bind
mounts or the Docker socket. Unknown descriptor fields are rejected rather
than ignored.

## Build and publish

The image build and upload do not change. After your existing image job, run:

```sh
npack-service.py build \
  --service-dir ./hello \
  --version 1.0.0 \
  --publisher npub1... \
  --image ghcr.io/acme/hello:1.0.0 \
  --output ./hello-1.0.0.npk

npack-service.py publish \
  --manifest ./hello-1.0.0.manifest.json \
  --secret-key "$NOSTR_SECRET_KEY" \
  --relay wss://relay.damus.io \
  --server https://blossom.primal.net
```

`build` resolves the image tag to its registry digest with
`docker buildx imagetools inspect`, falling back to the local image's repo
digest, then writes `.npack/manifest.json`, packs the `.npk`, and generates
the external manifest with its SHA-256. It requires the `npack` CLI
(`npack pack`, `npack manifest`).

Use a dedicated publisher key, not a personal identity. `npack generate-key`
creates one and registers it in the OS credential store. Publish with
`--secret-key` from a protected CI environment, never from a shell history
you keep.

A reusable workflow is at
`.github/workflows/publish-service-package.yml`. It checks out your service
repository, installs the pinned npack release, builds and (when
`NOSTR_SECRET_KEY` is configured) publishes the package.

```yaml
publish-package:
  needs: build-image
  uses: imattau/ncc-server/.github/workflows/publish-service-package.yml@v0.2.8
  with:
    version: 1.0.0
    publisher: npub1...
    image: ghcr.io/acme/hello:1.0.0
  secrets:
    NOSTR_SECRET_KEY: ${{ secrets.NOSTR_SECRET_KEY }}
```

`templates/ncc-service-npk/` is a working starting point with a `service.json`
and icon.

## The catalogue daemon

The bundle runs npack's read-only daemon in the `npack` Compose service:

- no Docker access and no package installation;
- non-root, read-only root filesystem, named volumes for state and the
  socket;
- relays and Blossom servers from `NPACK_RELAYS` and
  `NPACK_BLOSSOM_SERVERS`;
- a Unix socket at `/run/npack/npackd.sock`, mounted read-only into the
  sidecar.

The sidecar exposes `GET /ncc-api/catalogue` to the panel (NIP-98 authorized)
and uses the same daemon to resolve a package for the host installer. When
the daemon is missing, the panel says the catalogue is unavailable and every
other section keeps working.

A relay query can be slow, so `?refresh=1` starts the refresh and answers at
once with the listing the node already has plus `refreshing: true`. The
panel polls until the daemon writes the new catalogue, keeping the previous
listing on screen; a failed refresh returns `refreshError` and keeps the old
entries. The sidecar never holds the panel request open for the whole relay
query.

`NPACK_IMAGE` pins the daemon image, which currently installs npack 0.10.1
(`NPACK_VERSION` in `container/npack/Containerfile` and the workflow's
`npack_version` input). npack publishes amd64 Linux packages only, so the catalogue image is amd64-only; on an arm64 host the panel
reports the catalogue as unavailable and everything else keeps working. The
npack protocol is a project protocol, not a registered NIP yet, so the image
and the packaging script pin its release version together. Treat an npack
upgrade as a compatibility change.

## Install

On the host:

```sh
sudo make service-install REF=npub1.../hello@1.0.0
```

The sidecar resolves the release, downloads the `.npk` from the artifact URLs
in its signed `kind:1063` metadata, verifies the SHA-256, extracts exactly one
service descriptor, and returns it to the installer. The installer validates
the descriptor, creates the Compose fragment and Caddy listener, pulls the
image, waits for the probe, creates the NCC service record, publishes the
locator, and adds the service's onion.

For a local file (development only, no publisher signature):

```sh
sudo make service-install NPK=./hello-1.0.0.npk
```

Reading a local `.npk` needs `zstd` and `tar` on the host. The `REF` path does
not.

`make service-add PACKAGE=dir` still installs an operator-authored package
with its own `compose.yaml`, as described in
[custom Compose services](custom-compose-services.md).

## Trust

The publisher key is the identity. The panel shows:

- **Official** for the key in `NCC_NPACK_OFFICIAL_PUBLISHER`;
- **Trusted** for keys the operator trusted in the panel;
- **Unknown publisher** otherwise.

The official key is always trusted. Other publishers need
`PUT /ncc-api/catalogue/trust` from an admin key, or the Trust button in the
package dialog. The trust list is stored in the sidecar database, not in the
repository.

Installing from the host CLI always prints the publisher, version, image
digest and ports, and asks for confirmation unless `YES=1` is passed (for
example `sudo make service-install REF=… YES=1`). A package that is not
publisher-signed is labelled as such.

Trusting a publisher trusts the **metadata**. The image itself is a separate
decision: the panel shows the digest, and the container runs with the
sandbox described above, but the publisher's code still runs on your host.

## What is not supported

- One Compose service and one HTTP backend port per package.
- No publisher-supplied Compose text, host networking, extra capabilities or
  bind mounts.
- npack's catalogue hides revoked releases, so an **already-installed**
  service is not flagged as revoked yet. `make service-install` refuses a
  revoked release because resolution fails.
- No automatic updates. Re-run `service-install` with a newer version; the
  staged package keeps its previous release for rollback.

These are deliberate limits for the first release and match the existing
custom-service scope.
